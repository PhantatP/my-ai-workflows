# V2.5 — Artifact Lifecycle and Provenance

**Status:** Experimental
**Scope:** Cross-domain information management for BUILD, RESEARCH, LEARN, and general assistant use.

## Purpose and boundary

This experiment governs information intended to persist beyond the immediate
interaction. It asks what an artifact does, how it should evolve, which context
owns it, where local conventions place it, and how its provenance and
relationships survive change.

It does not replace domain correctness: BUILD still verifies artifacts,
RESEARCH still verifies evidence-backed conclusions, and LEARN still verifies
independent learner capability.

```text
Persistent information
→ classify role
→ choose lifecycle
→ resolve context
→ follow local placement conventions
→ preserve provenance and relationships
→ evolve by update, snapshot, promotion, archive, retention, or removal
```

Classify by artifact role and lifecycle, resolve context, respect local
conventions, then place and link the artifact. Avoid both root dumping and
turning every small note into a formal knowledge-management object.

## Artifact roles

Roles describe what an artifact does, not which domain created it.

| Role | Meaning | Default behavior |
| --- | --- | --- |
| `capture` | Information whose durable destination or importance is unclear | Use Inbox or an established capture location; do not invent structure. Write directly to a known destination when context is already clear. |
| `working` | Active thinking, drafts, plans, scratchpads, or task state | Keep near the active project or area; later merge, promote, archive, remove, or retain as appropriate. |
| `source` | Original external material used as evidence or input | Keep distinct from synthesis, preserve identity and origin, and prefer project-local source storage when ownership is strong. |
| `reference` | Structured information intended for later consultation or refresh | Update an existing canonical reference; keep freshness visible when time-sensitive. |
| `decision` | A durable choice or conclusion whose reasoning may matter later | Preserve the choice, rationale, assumptions, evidence, alternatives, and change conditions when relevant; keep it near what it governs. |
| `knowledge` | Distilled understanding intended to remain reusable | Promote only when genuinely reusable; polished assistant output is not automatically knowledge. |

Inbox is an uncertainty buffer, not a required gateway and not a folder only
for human-authored notes. Human and assistant artifacts use the same model.

## Lifecycle classes

Lifecycle describes how an artifact should evolve.

| Lifecycle | Meaning | Write behavior |
| --- | --- | --- |
| `ephemeral` | Temporary support for current work | Discard, merge, archive, or promote later. |
| `living` | A canonical artifact expected to change with reality or understanding | Update it rather than creating dated duplicates; preserve still-valid information. |
| `snapshot` | A point-in-time state whose history matters | Create a new snapshot; do not overwrite prior states. |
| `immutable` | Retrieved original evidence | Preserve the retrieved form; transformed representations retain the same source identity and provenance. |
| `durable` | Long-lived, conceptually stable information | Refine carefully without casually destroying rationale or provenance. |

Role and lifecycle are independent. A company dossier may be a living
`reference`; a portfolio review a snapshot `working` or `decision` artifact; an
annual report an immutable `source`.

## Context and placement

Resolve the strongest ownership before writing:

1. Strong active-project context → prefer project-local placement.
2. Ongoing responsibility without a finish line → prefer its Area or equivalent.
3. Reusable information beyond one project → prefer Resources or equivalent.
4. Unclear ownership → prefer Inbox.
5. Do not create a Project or Area merely because a note mentions a topic.

The workflow defines semantics, not a universal directory tree. Inspect the
library, its rules, and project- or area-local conventions; reuse compatible
structure and create folders only when repeated utility justifies them.

```text
generic lifecycle policy
→ library conventions
→ project or area conventions
→ artifact context
→ destination
```

Semantic placement defaults are: captures to a capture location, working
material to its active context, strongly owned sources to project-local source
storage, broadly reusable references and knowledge to a resource location, and
decisions near what they govern. Archive inactive material according to local
conventions. These are not required folder names.

## Canonical artifacts and write modes

Before creating a durable `reference`, `knowledge`, or `decision`, check for an
existing artifact representing the same subject and role. Prefer updating the
canonical artifact over creating an overlapping source of truth.

- **CREATE** when no suitable canonical artifact exists, a distinct source or
  decision exists, or a new artifact is otherwise semantically distinct.
- **UPDATE** when new information refreshes or extends a canonical living
  artifact. Preserve still-valid content, useful history, and provenance while
  correcting stale facts.
- **SNAPSHOT** when historical state or periodic comparison matters, or the
  user asks for a point-in-time record.
- **DO NOT OVERWRITE** immutable sources, historical snapshots, or anything
  whose replacement would destroy provenance.

A comparative synthesis may link canonical subject references, but must not
silently become another independent source of truth for those subjects.

## Source contract

Sources remain identifiable and separable from synthesis.

1. Preserve source identity and origin.
2. Prefer stable identity in this order when available: DOI; official document
   or report identifier; canonical URL; repository or document identifier;
   otherwise title, publisher, and date.
3. Keep source material separate from synthesis.
4. Keep material factual claims traceable to evidence.
5. Reuse an existing source identity instead of duplicating it.
6. Treat transformed files as representations of the same underlying source.
7. Create a dedicated source record only when reuse, importance, local
   archival, or auditability warrants it.

### Source tiers

An inline link is sufficient for one-off, low-reuse evidence. Use a canonical
source record for frequently reused or consequential material such as annual
reports, filings, papers, standards, important documentation, locally archived
sources, or evidence central to a decision.

Useful optional fields include:

```yaml
type: source
source_id:
source_kind:
source_level:
title:
publisher:
published:
accessed:
url:
local_file:
```

Use only fields that add value. Source level (`PRIMARY`, `SECONDARY`, or
`TERTIARY`) informs provenance and evidence strength; it does not determine
truth by itself.

### Representations and evidence locators

Compression, extraction, OCR, conversion, and summarization do not create a
new underlying source. A derived representation records the shared `source_id`,
its transformation, its origin, and retrieval date when relevant.

```yaml
source_id: toyota-annual-report-2025
representation: extracted-markdown
derived_from: original
```

A source is the external artifact; evidence is the portion supporting a claim.
Use locators proportional to consequence—for example a report section, paper
table, repository file and symbol, or other stable location. Exact paragraph
locators are unnecessary for low-consequence work.

Material factual claims that may influence future reasoning, decisions, or
durable knowledge remain traceable. Distinguish fact, interpretation,
inference, and prediction when that distinction matters; never present an
inference as directly sourced fact. Presentation-local numbering may be used,
but should not be the only identity for an important reusable source.

## Evolution and autonomy

Promote an artifact only after it demonstrates reuse, applies beyond its
originating task, is sufficiently stable, and has a clear canonical
destination. Propose ambiguous promotion instead of moving existing material.

Agents may normally classify and place new artifacts, update clearly canonical
living artifacts, preserve sources under existing conventions, deduplicate
identical source identities, and route uncertain captures to Inbox.

Agents remain conservative about moving human-created notes across contexts,
merging competing canonical artifacts, deleting or archiving meaningful
content, restructuring libraries, globally promoting project-local material,
or inventing large taxonomies. Ask or propose when intent is uncertain and the
change would materially alter existing organization.

Inbox should be processed over time through clarification and classification,
then placement, merge, archive, or deletion. Do not force classification during
rapid capture, but do not treat Inbox as permanent storage by default.

## Cross-domain examples

| Domain | Example mappings |
| --- | --- |
| BUILD | implementation plan → `working`; architecture choice → `decision`; official API documentation → `source`; project contract → `reference`; reusable engineering principle → `knowledge` |
| RESEARCH | scratchpad → `working`; annual report or paper → `source`; company dossier → `reference`; investment choice → `decision`; valuation concept → `knowledge` |
| LEARN | session notes → `working`; textbook or lecture → `source`; topic guide → `reference`; durable mental model → `knowledge` |
| General assistant | any role, determined by use rather than by the assistant operation |

An Obsidian/PARA library might map uncertain capture to `01 Inbox`, active
outcomes to `02 Projects`, ongoing responsibilities to `03 Areas`, reusable
material to `04 Resources`, inactive material to `05 Archive`, and generally
unowned binaries to `90 Assets`. This is an example only; a strongly owned
source may belong inside a project, and folders need not exist before use.

## Failure modes

- root dumping;
- domain-based placement;
- taxonomy explosion or metadata ceremony;
- duplicate canonical artifacts;
- source/synthesis mixing or provenance loss;
- treating derived representations as independent sources;
- premature knowledge promotion;
- permanent Inbox burial;
- aggressive moving, merging, deletion, archiving, or restructuring.

## Initial validation

Validation should use real work, not specification quality. Controlled prompts
may check capture routing, living-reference updates, source preservation,
LEARN working-versus-knowledge decisions, project-local BUILD decisions,
uncertain captures, and snapshot-versus-living behavior, but do not
automatically count as qualifying evidence.

For a genuine case, record only what is useful:

```text
Date:
User objective:
Domain:
Artifact:
Role classification:
Lifecycle classification:
Context:
Destination:
Existing canonical artifact found?:
Write mode: create / update / snapshot / none
Source/provenance handling:
User correction required?:
Friction: GOOD / MIXED / POOR
Outcome: useful / mixed / not useful
Representative exchange or artifact reference:
Failure category:
Notes:
```

Track `INITIATED`, `COMPLETED`, and `QUALIFYING` separately. This initial V2.5
change establishes the policy only; detailed validation is deferred.

## Patch discipline and promotion gate

Do not change the taxonomy after every unusual case. Patch it after the same
material failure appears in at least two independent real-use cases, or after
one failure creates correctness, provenance, destructive-action, safety, or
irreversible-loss risk. Prefer clarifying an existing rule to adding a role,
lifecycle state, or router.

Consider `PROMOTE`, `KEEP EXPERIMENTAL`, `REVISE`, or `REJECT` only after
real-use evidence shows whether the model generalizes across domains, improves
placement, reduces canonical duplication, preserves provenance and source
representations, handles living versus snapshot behavior, uses Inbox without
burying material, respects local conventions, works for both lightweight and
serious evidence, avoids bureaucracy, and remains conservative about
structural or destructive changes. Benefits must be attributable to this
policy rather than generic model behavior.

The goal is not perfect taxonomy. Persistent information should have a
sensible home, a clear role, an understandable lifecycle, and enough
provenance to remain trustworthy when reused later.
